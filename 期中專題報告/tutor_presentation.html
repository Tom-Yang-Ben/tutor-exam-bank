這一切，起源於備課痛點

身為數理與物理家教，我們深知每一次實體測驗對學生的重要性。然而，傳統出題流程卻有著極高的行政損耗：

  • 公式排版崩潰：在 Word 裡手動輸入複雜幾何、直式分數與根式，耗時且排版易跑位。
  • 題目高度重複：紙本管理難以精確追蹤歷史作答紀錄，降低了測驗的實際診斷效果。
  • 製作成本高昂：針對一個特定章節出一份特訓卷，往往會消耗兩小時以上的時間。

開發挑戰一：生成公式的格式困境

當呼叫大型語言模型（LLM）對 PDF 進行去結構化拆解時，我們遇到了第一個技術瓶頸：分數與公式的二義性。

  • 斜線分數的死角： AI 為了追求簡潔，在生 JSON 題目時，常將分數輸出為水平斜線（如 π/2、101/210）。
  • Word 無法識別： 這種斜線字串到 Word 裡面會直接以純文字顯示，無法轉換為專業考卷標準的「直式分數」。
  • 圖表遺落： 原本的純文字 JSON 結構，無法直接關聯並導出 PDF 中的物理受力圖或幾何座標圖。
Technical Hurdles Slide 04

解決方案：系統級 Prompt 制約與資料預洗

1. 強制規範 LaTeX 規格

在傳給 Gemini 的系統指令中，追加「嚴厲」的格式限制，強迫其使用標準 LaTeX，完美避開了改動原本 JSON 架構的要求：

⚠️【格式限制】：
所有的分數請『嚴格』使用 LaTeX 格式：
\frac{分子}{分母}。
絕對禁止使用斜線。若有幾何圖表，請在題幹末端追加：[附圖描述: ...] 描述關鍵幾何特徵與座標。

2. 資料轉換過濾層

在 Node.js 後端建立預處理模組，利用精準的正則表達式將 LaTeX 分數轉換為自訂的 FRAC 中間格式，防止符號跳脫毀損：

str = str.replace(
  /\\frac\{([^}]+)\}\{([^}]+)\}/g,
  '[FRAC:$1|$2]'
);

*這一步將公式隔離，避免與後續特殊字元清理與安全性跳脫機制產生衝突。

開發挑戰二：檔案損毀與 XML 的相容性死角

在整合匯出 docx 二進位流的過程中，我們面臨了最為棘手的檔案毀損問題：

  • MathRun 的物件相容性地雷 (導致毀損的主因)：
    套件中一般的 TextRun 需要傳入物件參數 { text: "字串" }。但 docx 底層的 MathRun 卻只允許直接傳入純字串。一旦傳入物件，產出的 XML 將包含非法空殼節點，Word 會判定檔案損毀拒絕開啟。
  • 系統環境產生的隱藏控制字元：
    使用原生 Javascript 的 toLocaleDateString() 格式化檔名時，部分 Node.js 執行環境會夾帶隱形的左右書寫方向控制字元，使 Word 文件結構標籤解析失敗。
  • 解答區排版遺漏：
    原先的公式渲染僅針對「題幹」處理，導致解答區中的 LaTeX 分數直接暴露為生硬的 FRAC 中間標籤。
XML Structural Integrity Slide 07

解決方案：解耦文字與數學公式的渲染組件

建立通用渲染組件 buildParagraphComponents

為了徹底解決 XML 損毀與排版遺漏問題，我將所有文字清洗與分數拆解的邏輯，抽離成獨立的共用函式：

修正 MathRun 傳值：遇到 LaTeX 分數標記時，調用 MathFraction 並在子節點傳入純字串型式的 new MathRun(numerator)，完美修復了 Word 開啟檔案損毀的底層缺陷。

解決時區亂碼：改用確定的 YYYY_MM_DD 格式字串拼接檔名，主動過濾隱形標記。並將此解析器同時套用在「題幹渲染」與「解答渲染」，確保了整張試卷格式的一致性與安全性。
