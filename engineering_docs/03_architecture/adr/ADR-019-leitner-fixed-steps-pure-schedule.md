## 1. 背景與問題

- **上下文**: DEC-016 要求「錯過的題要練到會為止，依間隔複習排程回測」；DEC-003 例外條款讓同一題可以再派給同一位學生，派題與作答拆表（[ADR-018](./ADR-018-assignment-attempt-split-compat-view.md)）。系統要決定每一題錯題「什麼時候該再考、考到什麼程度算會」。
- **問題**: 用什麼排程演算法、排程狀態怎麼存，才能讓老師看得懂每一題為什麼今天到期、改判或刪卷之後不會留下算錯的狀態、之後想換演算法也不會丟資料？
- **驅動因素/約束**:
  - 家教的節奏：紙本、一週一到兩次課。「7 天後到期」和「9 天後到期」實際上都是等下一次上課，排程只需要以週計。
  - 資料很少：一位學生一週約 20～40 題，一題錯題一輩子只重練幾次；需要用大量作答校準參數的演算法會長期不準。
  - 一題錯題是一整道數理題，學生會記得解法甚至答案；要隔開時間再考，才分得出「真的會」與「剛看過」。
  - 批改可以改判、取消，卷可以刪，學生可以合併；排程不能因為事件的先後而算出不同的結果。
  - 不新增 npm 依賴、不呼叫 LLM（本機模式與 Gemini 模式行為相同）。
  - Owner 2026-09-26 決策單第三輪：R1 選 2（老師在批改卡勾「要重練」才進清單）、R2 選 1（只有全對才算對）、R3 選 2（對 3 次：重做、隔 1 週、再隔 2 週）、R4 選 1（又錯回第一關，錯滿 3 次標卡關、仍留在清單）、R5 選 1（固定關卡，排程是作答歷史的純函式）。

## 2. 考量的選項

### 選項一: 固定間隔表（1／3／7／14／30 天）
- **描述**: 每題依第幾次複習套同一張間隔表，錯了從頭。
- **優點**: 最簡單、好解釋。
- **缺點**: 間隔表以「天」設計，3 天這一格在一週一次課時幾乎用不到；沒有「狀態」的概念，答錯怎麼處理要另外定。
- **成本/複雜度**: 低

### 選項二: 固定關卡（Leitner 式），排程是作答歷史的純函式（採用）
- **描述**: 每題在第 k 關，每關一個固定間隔；答對升一關、答錯回第 1 關；連對 K 次畢業。狀態（關卡、到期日、連對、錯的次數）一律由「這位學生這一題的全部作答」重算，資料表只存快取與老師的手動決定。
- **優點**: 狀態就是「第幾關」，老師一眼看得懂；決定性、可重算；不需要校準、不需要新依賴；間隔可以直接對齊上課節奏。
- **缺點**: 不會因人、因題調整間隔。
- **成本/複雜度**: 低

### 選項三: SM-2 簡化版（Anki 早期）
- **描述**: 每題一個難易係數，下一次間隔＝上一次間隔×係數，答題品質（0～5）調整係數。
- **優點**: 常錯的題間隔自動變短。
- **缺點**: 紙本只有對錯與部分給分，答題品質要硬湊；係數要好幾次作答才穩；「為什麼是 11 天」很難解釋；微調的好處被「等下一次上課」吃掉。
- **成本/複雜度**: 中

### 選項四: FSRS（ts-fsrs）
- **描述**: 以記憶模型預測遺忘機率，排到快忘的時候。
- **優點**: 理論上最省複習次數。
- **缺點**: 要新增 npm 依賴；參數要用大量作答資料訓練（原本針對單字卡）；老師無法檢查排程理由。
- **成本/複雜度**: 高

另一個正交的選擇是**狀態怎麼存**：把排程狀態當成真相、每次批改就地更新（簡單，但改判、取消批改、刪卷、合併學生時要寫各自的「倒退」邏輯，漏一處就留下錯的狀態），或讓狀態是作答歷史的純函式、表上只存快取（採用）。

## 3. 決策

**選擇**: 選項二——固定關卡（Leitner 式），排程是作答歷史的純函式。

| 參數 | 值 | 依據 |
| :--- | :--- | :--- |
| 關卡間隔 | 第 1 關＝下一份卷（派題日＋1 天）、第 2 關 7 天、第 3 關 14 天 | R3 選 2 |
| 畢業 | 連續全對 3 次＝練到會，不再到期 | R3 選 2 |
| 算對 | 已批改且 `COALESCE(score, result) ≥ 1`（沒給部分分且按「對」，或給 100%） | R2 選 1 |
| 又錯 | 回第 1 關、連對歸零、錯的次數＋1 | R4 選 1 |
| 卡關 | 進行中且錯的次數 ≥ 3：只提醒，仍在清單、照樣到期 | R4 選 1 |
| 進清單 | 由老師決定（批改卡勾「要重練」、清單上手動加入）；排程函式只從起算日開始算，新題那一次的對錯不影響排程 | R1 選 2、R11 選 3 |
| 附在新卷的預設上限 | 新題數 × 0.3，無條件捨去，且新題＋重練 ≤ 50 題 | R6 選 1 |

**理由**:
- **老師看得懂、改得動**：清單上每一題都能說出「第 2 關、上次 10/5 答對、所以 10/12 到期」；參數集中在 `config/retrain.js`，可用環境變數覆寫（`RETRAIN_STEP_DAYS`、`RETRAIN_MASTERY_STREAK`、`RETRAIN_STUCK_LAPSES`、`RETRAIN_ATTACH_RATIO`；非法值退回預設並警告一次），改完執行 `npm run retrain:recompute` 就照新參數重排。
- **決定性，與事件先後無關**：`computeRetrainState({ entered_on, teacher_override, override_on, history }, params)` 不碰 DB、不讀 env、不看時鐘；歷史在函式內依（派題日, 派題編號）排序，所以改判、取消批改、刪卷、合併之後重算即可，結果與「從頭依序批改一次」相同（不變量 I7）。這一點以固定種子的 1,000 組隨機歷史對照另一種寫法的參考實作釘住。
- **不會丟資料**：真相是作答歷史，排程表只是快取；之後若資料量變大、想換成 SM-2 或 FSRS，改的是一個純函式，重算即可。
- **老師的決定優先**：移出、判定已會、重新加入另存（`teacher_override`、`override_on`），重算時最後套用；系統只提醒（到期、卡關），不替老師放棄一題（DEC-016「練到會為止」）。
- **日期與時區**：日期一律是 `'YYYY-MM-DD'` 字串，以 UTC 做日數加減，伺服器在哪個時區結果都一樣。

## 4. 後果

- **正面**: 規則短、可解釋、可測：第 4.5 節的例子逐列釘在單元測試；參數化測試證明 Owner 改設定（K＝2／4、不同間隔表）不需要改程式；排程從歷史重算，改判與刪卷不會留下錯的狀態；零新依賴、零 LLM 呼叫。
- **負面**: 不會因人因題調整間隔；照 Owner 選的參數，附在新卷的三成一週只消化得了重練量的約 1/3～1/6，其餘大約每週要出一份獨立重練卷（設計稿第 4.8 節；R1 選 2 讓進清單的題比「答錯全進」少，實際份量看 API-13 的 `backlog`）；同一天的多筆作答各算一次（到期機制平常不會這樣排，老師手動提早出題時由老師決定）；錯的次數在重新加入後不歸零，重新加入的題可能一開始就標卡關；排程快取要在觸發它的同一交易內重算（批改、刪卷、合併、手動決定），PR-2 的 I/O 層必須守住這一點。
- **影響範圍**: 已交付：`exam_pro/config/retrain.js`、`exam_pro/services/retrainSchedule.js`、`test/unit/retrainConfig.test.js`、`retrainSchedule.test.js`、`retrainScheduleProperty.test.js`。之後：M2（`retrain_items`）、`services/retrainService.js`（I/O）、批改／刪卷／合併掛鉤、API-1～13、`npm run retrain:recompute`（設計稿第 5 節）。
- **重新評估觸發**: 成效統計顯示到期清單持續越堆越多、或卡關比例過高；學生端自助作答上線、作答量足以校準 SM-2／FSRS；Owner 想依錯因或題型調整間隔；Owner 決定改用變式做回測（R9 的選項 2，追蹤單位從「題」改成「家族」）。
