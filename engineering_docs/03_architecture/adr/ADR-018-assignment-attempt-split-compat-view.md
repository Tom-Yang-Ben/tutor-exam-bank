## 1. 背景與問題

- **上下文**: `attempts`（`migrations/0001`，`0010` 加批改細節）是**一列＝一位學生被派到一題**，派題與作答混在同一列；`UNIQUE (student_id, question_id)` 是 DEC-003「不重複出題」的伺服器端硬閘門，`writePaper` 以 `ON CONFLICT DO NOTHING`＋寫入筆數檢查在兩個出卷請求搶同一題時回 409。這張表被 20 多處讀寫：排除（候選池、找相似、NLQ、變式檢索、覆蓋率、補救卷、刪題保護，共八處）、診斷（弱點面板、知識點掌握度、補救卷基底、家教的錯因摘要，含凍結的 SQL）、卷層（試卷明細、批改、學生清單、助教）與寫入（出卷、刪卷、刪學生、合併學生、批改），另有 23 個測試檔的夾具（設計稿第 2.3 節）。
- **問題**: DEC-003 例外條款（Owner 2026-09-24 選 a：拆表；2026-09-25 核准）要求「錯題重練與間隔複習可再出同一題、每次作答各自記錄；新題組卷仍排除已作答」。唯一約束讓重派必定 409，批改又直接覆寫那一列，第二次作答會蓋掉第一次。要怎麼讓同一題可以再派、每次作答各自留下，同時新題仍然每生每題一次、由資料庫硬擋，而既有的讀法與數字都不變？
- **驅動因素/約束**:
  - DEC-003 原條文的硬閘門不得鬆：「新題每生每題一次」仍要由資料庫保證，不能只靠程式。
  - Owner 2026-09-26 決策單第三輪 R10 選 1：弱點面板與補救卷只算每題「第一次」作答；重練成效另外看。
  - 沒有重練資料時，所有既有 API 的回應、數字與行為要與現在逐字相同；既有測試不得放寬（NFR-009 的精神）。
  - migrations 只增不改（NFR-006）；`migrate.js` 一支一交易，失敗要能整支回滾。
  - 日後學生端自助作答（G24）可能需要「同一次派題作答多次」。

## 2. 考量的選項

### 選項一: 單表加欄
- **描述**: `attempts` 保留為實體表，加 `purpose`（new／retrain）欄，把唯一約束改成只管新題的部分唯一索引，另加 `(paper_id, question_id)` 唯一。
- **優點**: 改動量最小，測試夾具幾乎不用改。
- **缺點**: 不符合已核准的驗收文字「資料層拆分派題與作答」；學生端若要同一次派題作答多次還得再拆一次；弱點只算第一次作答時，十多處凍結的診斷 SQL 都要加 `purpose = 'new'` 條件。
- **成本/複雜度**: 低（保留為 PR-1 成本失控時的退路，但要先修訂 DEC-003 的驗收文字）

### 選項二: 另開重練表（DEC-003 選項 b）
- **描述**: `attempts` 與唯一約束原封不動，重練的派題與作答寫另一張表。
- **優點**: 既有程式完全不動。
- **缺點**: 作答紀錄分散兩處，卷層讀取與成效統計都要合併兩張表。Owner 2026-09-24 已否決。
- **成本/複雜度**: 中

### 選項三: 只用變式重練（DEC-003 選項 c）
- **描述**: 不重出原題，改出同家族沒寫過的變式。
- **優點**: 資料層不用改。
- **缺點**: 家族互斥擋住同卷集中練；看不到同一題有沒有進步；很多題沒有變式。Owner 2026-09-24 已否決（2026-09-26 R9 也選「這一輪一律用原題」）。
- **成本/複雜度**: 低（資料層）／高（依賴變式品質）

### 選項四: 拆成派題表與作答表，`attempts` 改為唯讀相容檢視（採用）
- **描述**: 新表 `assignments`（派題：學生、題目、卷、派題日、用途 new／retrain）與 `attempt_records`（作答：對錯、部分給分、錯因、學生答案、註記，與派題一對一）。舊資料以原 id 搬移並在同一支 migration 內逐欄自我檢查，不一致就 RAISE 整支回滾。`attempts` 這個名字留給唯讀檢視，只列 `purpose = 'new'` 的派題（每生每題最多一列＝舊表語意），另建 `assignment_attempts` 檢視含全部派題。新題閘門改成 `assignments (student_id, question_id) WHERE purpose = 'new'` 的部分唯一索引；「每一筆重練派題，同生同題一定有一筆新題派題」（不變量 I1）由重練派題 → 排程項目 → 新題派題的複合外鍵保證。
- **優點**: 見第 3 節。
- **缺點**: 見第 4 節。
- **成本/複雜度**: 高（M1 migration、寫入點與卷層讀取改寫、23 個測試檔的夾具改走 helper）

## 3. 決策

**選擇**: 選項四——拆表，以相容檢視保留既有讀法。

**理由**:
- **排除查詢一個字都不用改**：有了 I1，「這位學生有沒有這一題的新題派題」與「這一題有沒有派給過他（任何用途）」永遠相等，所以八處 `NOT EXISTS (SELECT 1 FROM attempts …)` 繼續讀檢視就是對的。
- **診斷的口徑正好是 Owner 選的**：檢視只有第一次派題，弱點面板、知識點掌握度、補救卷基底讀它就是「只算第一次作答」（R10 選 1），凍結的 SQL 不用改、數字與現在相同。
- **硬閘門沒有鬆**：新題每生每題一次（I0）仍是資料庫的唯一索引；兩個出卷請求搶同一題時照舊 409、整張卷不寫入。
- **錯了會立刻被發現**：檢視是唯讀的，任何對 `attempts` 的 INSERT／UPDATE／DELETE／TRUNCATE 都會報錯，不會悄悄寫錯地方；另加單元測試掃描程式碼禁止這類語句。
- **效能不退化**：`attempt_records.assignment_id` 有唯一索引，查詢沒用到作答欄位時 PostgreSQL 會消去 LEFT JOIN，候選池的 `NOT EXISTS` 只剩一次部分唯一索引查找（以 EXPLAIN 斷言釘住）。
- **為學生端留路**：派題與作答分開後，日後要「同一次派題作答多次」只要放寬一對一（I4），不必再拆一次表。

## 4. 後果

- **正面**: 同一題可以再派、每次作答各自留下紀錄（看得到「第一次錯、第二次對」）；新題組卷照舊排除寫過的題且由資料庫擋；沒有重練資料時既有 API、數字與報表逐字不變；重練與成效統計有乾淨的資料來源（`assignment_attempts`）。
- **負面**: M1 要在一支 migration 內搬資料、刪舊表、建檢視（先備份、自我檢查、一支一交易）；卷層四處加助教一處改讀 `assignment_attempts`，寫入點全部改寫；23 個整合／e2e 測試檔約 46 處夾具改用 `test/helpers/attempts.js`；`schema.test.js` 三條結構斷言、`students.pg.test.js` 的 EXPLAIN 索引名、`controllers.pg.test.js` 的觸發器依本決策改寫（設計稿第 6.4 節逐條列出，驗的仍是同一件事或更多，沒有放寬）；`migrate/import_pg.js` 等 MySQL 切換的一次性工具在 M1 之後不再適用；與同一輪其他分支的測試檔衝突風險高，所以 PR-1 要等那些分支合併後再開。
- **影響範圍**: `exam_pro/migrations/`（M1：0016 之後的下一號）、`controllers/examController.js`（writePaper、confirmPaper、deletePaper）、`paperController.js`、`studentController.js`、`studentAdminController.js`、`services/assistantService.js`、`eval/lib/pgEngine.js`、`test/helpers/attempts.js` 與第 6.4 節列出的測試；實作為 PR-1（資料層，另一分支進行中）。
- **重新評估觸發**: 學生端自助作答需要同一次派題作答多次（放寬 I4）；PR-1 實際成本遠超預期（退路是選項一，但要先修訂 DEC-003 的驗收文字）；檢視展開後的查詢計畫在真庫退化到 NFR-010 草案的門檻以外；Owner 改變 R10 的口徑（B 類改讀 `assignment_attempts` 即可，不必改表）。
