## 1. 背景與問題

- **上下文**: 弱點面板（階段 3）能告訴老師「哪一章錯最多」，但組卷只收單一章節、章內等機率抽題，完全不讀弱點資料；流程斷在「再出卷」這一步（缺口 G04）。階段 5 加入知識點（`question_kcs`、`kc_prerequisites`）與部分給分（`attempts.score`），可以做到「依弱點一鍵出下一份卷」。
- **問題**: (1) 弱點要用什麼量排序，才不會被小樣本誤導？(2) 補救卷的選題要怎麼做，才不會和既有組卷的「不重複出題、家族互斥、承上題整組」規則分岔？
- **驅動因素/約束**:
  - 家教的樣本量很小：一位學生一章常常只批改過 1–5 題。「1 題對 1 題＝100%」會讓最不確定的單位被當成強項。
  - DEC-003 的不重複出題是 Owner 核准的硬閘門（`UNIQUE(student_id, question_id)`），補救卷不得繞過。
  - 家族互斥（階段 3）與承上題整組（FR-019）已有完整測試；再寫一份選題 SQL，兩份遲早漂移。
  - 知識點資料在上線初期可能是空的（標註還沒跑完），必須能退回章節。
  - 不得呼叫 LLM、不得讓既有 cassette 失效（契約第 1.1 條）。

## 2. 考量的選項

### 選項一: 依錯誤率（或答對率）排序，另寫一支補救卷專用的選題查詢
- **描述**: 沿用弱點面板的 `wrong_rate` 排序；補救卷自己組一條 SQL 抽題。
- **優點**: 直覺、實作最快；和弱點面板顯示的數字一致。
- **缺點**: 小樣本的比率極不穩定（1/1 與 0/1 分居兩端），排序會被噪音主導；另寫的選題查詢必須重做已作答排除、封存、題源、家族互斥與承上題整組，任何一處遺漏都是靜默錯誤（例如抽到孤兒承上題）。
- **成本/複雜度**: 低（初期）／高（維護）

### 選項二: 掌握度模型（BKT 或 IRT／Elo）
- **描述**: 以作答序列估計每個知識點的掌握機率，依機率排序；題目難度一併校準。
- **優點**: 理論上最精確，能利用作答順序與題目難度。
- **缺點**: 需要參數（BKT 的 slip／guess／learn）或大量作答資料校準；家教的樣本量撐不起 IRT；結果難以向老師解釋；缺口分析（G12）已建議先上 Wilson、資料夠了再上 BKT。
- **成本/複雜度**: 高

### 選項三: Wilson 下界排序＋以配額重用既有選題閘門（採用）
- **描述**: 每個單位（知識點或章節）以正確率的 Wilson 下界（z = 1.96）排序，知識點依 `question_kcs.weight` 加權、正確度取 `COALESCE(score, result)`；補救、先備、延伸三桶以最大餘數法分配題數，每個目標單位變成一段「配額」。選題把 `generate-paper` 的候選池 SQL 抽成共用函式（`buildCandidatePoolQuery`），多段配額依序走同一個 `pickPaperUnits`，跨段共用已選題與已占用家族的集合。
- **優點**: 小樣本自然得到低下界（1/1 → 0.21、8/10 → 0.49），排序保守而可解釋（「在 95% 信心下答對率至少多少」）；純函式、可單元測試；選題規則只有一份，`generate-paper` 的跨章配額（blueprint）也用同一套；知識點資料不足時退回章節，只是單位不同、演算法相同。
- **缺點**: Wilson 下界不看作答先後與題目難度；低樣本單位會被優先排入補救，可能把「其實會、只是寫得少」的單位也拿來補；配額是規則式（k = min(3, ⌈n/2⌉)、先備難度 ≤ 3 等），需要實際使用後調整。
- **成本/複雜度**: 中

## 3. 決策

**選擇**: 選項三——Wilson 下界排序弱點，補救卷與跨章配額組卷共用同一段候選池與同一個 `pickPaperUnits`；草稿只讀不寫，確認沿用既有 `confirm-paper`。

**理由**:
- 在家教的樣本量下，Wilson 下界是「比錯誤率穩、比模型簡單」的中間點，而且能一句話向老師解釋；缺口分析 G12 也建議先走這一步。
- 把候選池抽成共用函式後，單章組卷、跨章配額、補救卷三條路徑的排除規則只寫一次；單章路徑只帶 `chapters=[chapter]`、其他新條件為 NULL，行為與回應逐字不變（既有整合測試與 e2e 驗證）。
- 不足量逐目標回報、不自動拿別的單位補：補救卷是給老師審的草稿，悄悄換單位會讓「為什麼選這題」說不清楚。
- 只讀不寫、確認走既有 `confirm-paper`：寫入路徑維持唯一，DEC-003 的 `UNIQUE` 硬閘門與 409 行為不變。

## 4. 後果

- **正面**: 弱點面板到下一份卷的閉環成立（G04）；草稿每一題都帶 bucket 與目標單位、每個目標帶理由與不足量；跨章配額（`blueprint`）成為組卷 API 的一部分；新路徑零 LLM 成本、零 cassette 變動、零 migration。
- **負面**: `examController.selectPaperQuestions` 的 SQL 改為呼叫共用函式（候選池多了章節清單、難度下限、難度上限、知識點四個「NULL＝不限制」的條件，單章路徑語意不變）；補救卷的規則參數（k、難度區間、先備難度上限）寫在 `services/remedialService.js` 的常數，調整要改程式；低樣本單位偏向被補救，老師需要看「樣本不足」標記判斷；草稿交給老師刪題、加題之後，承上題整組的把關落在前端（草稿 `items` 帶 `follows_question_id`／`group_ids`，手動加題先查 `GET /api/students/:id/remedial-paper/items`），因為 `confirm-paper` 照給的題出卷、不重驗組是否完整（契約規定不改），直接呼叫 API 自行拼題的人仍可能出半組。
- **影響範圍**: `exam_pro/controllers/examController.js`、`exam_pro/services/kcWeaknessService.js`、`exam_pro/services/remedialService.js`、`exam_pro/services/coverageService.js`、`exam_pro/controllers/remedialController.js`、`exam_pro/routes/index.js`、`exam_pro/public/js/remedial.js`、`exam_pro/public/js/variants.js`（「加入補救卷」掛鉤）。
- **重新評估觸發**: 單一學生單一知識點的已批改題中位數超過 10 題（資料量足以估 BKT 參數）；或老師回報補救卷常把已精熟的單位排入；或錯題重練（G11，需 DEC-003 例外條款）上線，使同一題的多次作答成為常態。
