# 現場操作腳本（面試用）

對象是面試官，時間假設 20～30 分鐘。形式是**瀏覽器加桌面啟動器 A**（`docs/desktop-launcher.md`），在作者自己的 Windows 機器上實機操作。

本檔只寫「怎麼演」。系統本身的安裝與設定看 [`exam_pro/README.md`](../exam_pro/README.md)，本機模式的速度與限制看 [`local-mode.md`](local-mode.md)，各功能的契約看對應的專門文件。

---

## 0. 一個必須先承認的限制

這台電腦是純 CPU、只有內顯、16 GB RAM。本機模式的 AI 步驟**不是互動速度**：

| 步驟 | 實測／依實測速度估 | 來源 |
|---|---|---|
| PaddleOCR，1 頁 | 約 4 分鐘（含載入 1～2 分） | `local-mode.md` 10.12 |
| `extract_ocr` 整理，1 頁 10 題 | 約 15 分鐘（輸出約每秒 2 token、JSON 約 1,800 token） | 同上 |
| 分類，每題 | 51 秒（前綴快取熱）～約 7 分（整段冷） | `local-mode.md` 10.14 |
| 公式 lint，每題 | 只有規則修不好的題（約 10%～20%）才呼叫 LLM，一次 8～10 分 | 同上 |
| 驗算，每題 | 3～6 分（開思考，最久） | 同上 |

**所以「現場上傳一份考卷，等它跑完」是不可行的**：一般的 1 頁卷光拆題就 30～45 分鐘。腳本的設計前提就是這件事。

反過來說，**不呼叫 LLM 的功能全部是即時的**，而那些正好是教學價值最明顯的部分：

| 即時（可以現場隨意操作） | 慢（要另外安排） |
|---|---|
| hybrid 查題、相似題、自然語言查題 | 上傳 PDF 走拆題管線 |
| 智慧組卷、匯出 Word | 變式題生成 |
| 記錄作答、批改、錯題重練 | AI 助教問答 |
| 補救卷草稿、補救成效、學習報告 | |

## 1. 事前準備（面試前一天做完）

- [ ] `git --no-optional-locks status` 乾淨，在 `main` 上，CI 綠。
- [ ] 桌面圖示「出題系統」點一次能起來（Docker → PostgreSQL → Ollama → 後端 → 啟動頁轉首頁）。
- [ ] 題庫有資料：至少兩科、章節分布夠寬，能撐起章節篩選與相似題。
- [ ] **準備一位示範學生**，而且**要有作答與批改紀錄**——補救卷與學習報告沒有批改資料就只會顯示「資料不足」，那一段會演不出來。錯題要集中在一兩章，並標好錯因（觀念不清、計算錯誤之類），弱點面板與依錯因出題才有東西可看。
- [ ] **準備一份「1 題」的示範 PDF**（見第 3 節），放在好找的位置。
- [ ] **預跑一份同樣的卷並留在複核佇列**，當第 3 節的對照與退路。
- [ ] 學生姓名用化名（`exam_pro/utils/pseudonym.js` 只保護送進模型的那一段，畫面上顯示的是真名）。
- [ ] `.env` 不要開著給人看，裡面有金鑰。
- [ ] 瀏覽器只留一個分頁、縮放設到對方看得清楚的大小、關掉通知。

### 現場開場前 10 分鐘

- [ ] 桌面圖示點開，等後端起來。
- [ ] **預熱模型**：先讓 Ollama 載入 `qwen3:8b`、PaddleOCR 跑一次空轉。模型載入本身要 1～2 分鐘，這段沒有必要在面試官面前等。
- [ ] 把要用的頁面各開一次（題庫管理、智慧組卷、學生），讓前端資源與第一次查詢的快取都熱起來。

## 2. 建議的順序（20～30 分鐘）

先給結果，再給機制。面試官通常在前三分鐘決定要不要認真聽。

| 段 | 時間 | 做什麼 | 要讓對方看到什麼 |
|---|---|---|---|
| A | 2 分 | 開場：一句話說系統，點桌面圖示 | 「一個圖示把 Docker、資料庫、模型、後端依序開起來」——工程完整度，不只是一支腳本 |
| B | 4 分 | 題庫管理：查題、相似題、自然語言查題 | hybrid 檢索（向量 ＋ jieba 全文，RRF 融合）；golden 40 筆上 Recall@5 從 LIKE 的 0.8750 到 1.0000 |
| C | 5 分 | 智慧組卷 → 匯出 Word | **在 Word 裡點開一個分數，它是可編輯的原生方程式**，不是圖片。這一段最有說服力，因為是手寫的 LaTeX → OOXML |
| D | 5 分 | 學生：批改 → 弱點面板 → 依弱點出補救卷 → 補救成效 → 學習報告 | 「針對性」是算出來的，不是挑出來的：Wilson 下界選弱單位、錯因決定題型與難度、補救前後答對率有快照可比 |
| E | 6 分 | 拆題管線（見第 3 節） | 多 Agent 加硬閘門、部分入庫、人工複核佇列 |
| F | 3 分 | 收尾：eval 與 CI | 回放式 eval、門檻只升不降、CI 不連網也不需要金鑰 |

C 段和 D 段是這個系統和「一般題庫網站」差別最大的地方，時間不夠就砍 B 和 F，不要砍 C、D。

## 3. E 段：拆題管線怎麼演

目標是讓對方看到**管線真的在跑**，而不是看完一段錄影聽解說。做法是「現場啟動、不等跑完」。

### 3.1 用一份「1 題」的 PDF

不要用正常的考卷。自己排一份只有一題的 PDF，題目要有一個分數或根式（才看得出公式處理）。依第 0 節的速度推估，在模型已預熱的情況下：

| 步驟 | 推估 |
|---|---|
| PaddleOCR | 約 2 分（載入已預熱） |
| `extract_ocr` 整理 1 題 | 約 2 分（輸出約 200 token、每秒 2 token） |
| 分類 | 約 1 分（前綴快取熱） |
| 公式 lint | 多半不呼叫 LLM，規則就修好了 |
| 驗算 | 3～6 分 |
| **合計** | **約 8～13 分** |

**這幾個數字是用 `local-mode.md` 的實測速度推算的，不是端到端實測。** 面試前務必自己完整跑一次計時，把真實數字填回這張表。

### 3.2 等待時間講什麼

按下上傳之後，畫面停在 jobs 的狀態，節點會一個一個推進。這段時間照這個順序講，每一小段都可以被打斷：

1. **為什麼不讓 LLM 決定流程**。流程是程式寫的狀態機，8 個節點：`extract → dedup0 → classify → lint → source_check → verify → dedup1 → save`。LLM 只負責單一節點裡的判斷，節點之間的推進與放棄由程式決定。指著畫面上正在推進的節點講。
2. **每個 agent 是純函式，輸出先過 JSON Schema（ajv）與章節白名單**。模型講錯章名、少欄位，在進資料庫之前就被擋下來。
3. **硬閘門與部分入庫**。通過的題直接入庫，沒通過的附上 12 種 `review_reason` 之一停在人工複核。失敗不是整批退回。
4. **零成本閘門與證據否決**。拆題模型順手給的章節若信心夠就直接採用，省掉一次 LLM 呼叫；但若題幹連一個那一章的線索都沒有，否決它、改走第二層（`utils/chapterPostRules.js` 的 `gateEvidenceVeto`）。這是「便宜的路要有防線」的例子。
5. **worker 的認領**：`FOR UPDATE SKIP LOCKED` 加租約，中斷之後可以接著跑。
6. **本機模式的取捨**：OCR 為主，所以沒有第二條路可以互相比對，因此**每一題都要人工確認**才入庫。這是刻意的，不是沒做完——實測看圖拆題 1 頁 54 分鐘且輸出的 JSON 不合法之後的決定。

### 3.3 不要等它跑完

講完架構就切到**預先跑好**的那一份卷：

- 複核佇列：每一題的 `review_reason`、原卷比對的結果、哪些題通過了哪些沒有。
- `npm run report:jobs` 的輸出：各 agent 的延遲 p50／p90／max、每秒 token 數。**這張表比任何口頭說明都有力**，它證明這些數字是量出來的。

然後回頭看現場那一題跑到哪了。跑完就展示它的產出，沒跑完就說明還在哪個節點——**兩種情況都不尷尬，因為對照組已經看完了**。

## 4. 預期會被問到的，以及該怎麼答

| 問題 | 重點（細節在括號裡的文件） |
|---|---|
| 為什麼不用現成的 RAG 框架？ | 需要的是「同一段 SQL 讓 API 與 eval 共用」與可量測，不是抽象層。hybrid 寫在 `queries/hybrid.js`（`retrieval.md`、`rag-and-agents.md`） |
| 怎麼知道有沒有變好？ | 5 個 eval suite 對人工定案的 golden 量測，門檻寫在 `eval/thresholds.json`，只升不降。CI 讀 cassette，找不到就失敗，不會偷偷改去呼叫模型 |
| 為什麼不用雲端模型？ | 題目是學生的資料；而且要能離線、零邊際成本。代價是慢，所以拆題改成 OCR 為主並要求逐題人工確認 |
| 這樣慢到不能用吧？ | 慢的只有入庫那一次。日常使用的查題、組卷、匯出、批改、報告都不呼叫 LLM，是即時的 |
| 測試數字可信嗎？ | CI 上三個 job（unit 跑 Node 22／24、integration 用 pgvector service、desktop），不需要金鑰、不連網。README 的評測數字是 main 上照 CI 設定實跑的 |
| 一個人做的？ | 需求、架構、實作、評測都是；需求、架構決策（ADR）與追溯 ID 另有一套內部工程文件，未隨 repo 公開 |

## 5. 退路

| 意外 | 怎麼辦 |
|---|---|
| Docker 或 Ollama 起不來 | 不要現場排除。改用 `demo_video/` 的錄影，並說明那是同一套系統。**錄影是 2026-08-24 錄的，不含補救卷與學習報告**，要先重錄或口頭補充 |
| 現場那一題卡住或逾時 | 正是講「硬閘門與人工複核」的機會：它停在複核佇列而不是寫進一筆錯資料 |
| 時間只剩 10 分鐘 | 只演 C（組卷 → Word）和 D（學習報告），其餘用 README 的架構圖講 |
| 對方想看程式 | 開 `queries/hybrid.js`（一段 SQL 做 RRF）、`agents/classify.js` 的兩層分類、`utils/textFormatter.js` 的 `parseLatexToMath`（手寫解析器直接產 OOXML 數學物件） |
